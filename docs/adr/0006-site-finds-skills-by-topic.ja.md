# 0006. サイトはGitHubのトピックmusubi-skillsでスキルを見つける

## 決めること

誰のスキルでも、PRもデータベースも使わずにサイトへ載せる方法。

## 採った案

オーナーが`pnpm site:publish`を実行すると、ビルドはオーナーのghのログインで、トピック`musubi-skills`を持つ公開リポジトリをGitHubで検索する。
見つけたリポジトリのデフォルトブランチで`musubi.json`と`SKILL.md`が並ぶフォルダを、`musubi check`と同じ決まりで`musubi.json`を確かめてから載せる。
通らなかったフォルダは、ビルドの出力に理由と一緒に名前を出して外し、`registry/excluded.json`には載せないリポジトリとフォルダを書く。
`registry/<owner>/<repo>.json`には管理者のスキルを書き続け、両方に出てくるフォルダは1回だけ載せる。
一覧とスキルのページには、スキルの内容と安全性を誰も確かめていないことを表示する。

## 却下した案

| 案 | 採らない理由 |
|---|---|
| GitHubのコード検索で`musubi.json`を持つ公開リポジトリを全て見つける | コード検索のAPIは2026年に作られたリポジトリを検索の対象に入れておらず、最初のスキルを置いたリポジトリも対象の外にある |
| `registry/<owner>/<repo>.json`を追加するPR | 作者が皆PRを送ることになり、レビューせずにマージするとサイトのコードを書き換えられる |
| `agent-skills`のような広いトピックを持つリポジトリを全て走査する | 1回の公開で数千のファイルの一覧を読むので、GitHubの1時間5000回の上限に当たり、30分以上かかる |
| 登録を保存するCloudflare Workersのサービス | スキルはGitHubのリポジトリに置かれたマーケットプレイスで配るので、GitHubを読めば足りる |
| トピックを付ける`musubi register`のコマンド | トピックはリポジトリのAboutの設定で1回付けるだけで済む |

## 根拠

- Issue #20の決めたことの表。誰でもスキルを載せてよく、管理者はスキルを確かめも保証もせず、作者はPRを送る代わりにリポジトリにトピックを付けると決めた。
